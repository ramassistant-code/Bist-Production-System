Add a simple login screen: username = email, password. Also add an admin action to set an initial password for a user.

Do NOT create a password column or password table anywhere in the public schema. Use Supabase Auth's built-in email/password authentication (supabase.auth.signInWithPassword) as the sole place passwords are stored and verified — it already exists in this project and handles secure password hashing. Do not build any custom password hashing/storage.

Login screen:
1. Hebrew RTL page with two fields: אימייל (email) and סיסמה (password), and a "התחברות" button.
2. On submit, call supabase.auth.signInWithPassword({ email, password }).
3. If it fails: show a generic Hebrew error ("אימייל או סיסמה שגויים") — do not reveal whether the email exists or not.
4. If it succeeds: look up app_users by email (case-insensitive) and require is_active = true and deleted_at is null.
   - If a matching active app_users row is found: allow access into the app.
   - If Supabase Auth succeeded but there is no matching active app_users row: sign the user out immediately and deny access, with a clear Hebrew message ("האימייל הזה אינו רשום כמשתמש פעיל במערכת. פנה למנהל המערכת.").
5. Do not implement any role-based access differences yet — every user who passes step 4 gets the same access, regardless of their role value in app_users. Role-based permissions are a future milestone.

Admin "set initial password" action (in the Settings › users screen):
1. For each user in app_users, add an action "הגדר סיסמה ראשונית" (admin-only for now, since there is no role enforcement yet — just make sure this action is not reachable from the regular login screen).
2. This must go through a backend API route (never from the frontend) that uses SUPABASE_SERVICE_ROLE_KEY to call the Supabase Auth Admin API:
   - If no auth.users account exists yet for that email, create one with the given password (supabase.auth.admin.createUser).
   - If one already exists, update its password (supabase.auth.admin.updateUserById).
3. The admin types the initial password in a simple form field (min length validation only, e.g. 8+ characters) and submits — show a Hebrew success message when done.
4. Never log or store the plaintext password anywhere outside that one request to the Supabase Admin API call.

Bootstrapping the very first password (chicken-and-egg problem):
There is no logged-in admin yet to use the "set initial password" action, and there is no role enforcement yet either. Handle this explicitly:
- Provide a one-time, clearly-documented way to set the first password — for example a small seed/setup script (run once from the server environment, using SUPABASE_SERVICE_ROLE_KEY, never exposed to the frontend) that sets a password for a specific existing app_users email passed as an argument or env variable.
- Do not leave the "set initial password" admin action reachable without any login at all from the UI — it should still require being logged in as *some* valid app_users, even though there's no role check yet distinguishing admins from others. The one-time seed script is the only way to get the very first working login.
- In your milestone report, give explicit step-by-step instructions for how the user should run this seed step to create their own first login before anyone else can use the "set initial password" UI action.
- Note clearly in the report that once role-based permissions are implemented in a future milestone, the "set initial password" action must be restricted to admin role only.

Rules:

- Never expose SUPABASE_SERVICE_ROLE_KEY to the frontend — the admin password-setting logic must run server-side only.
- Do not touch the quotes, customers, leads, products, or components screens.
- Keep the UI Hebrew RTL, consistent with the rest of the app.

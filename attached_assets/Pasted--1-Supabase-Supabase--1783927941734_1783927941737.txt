# שלב 1 – תיקון תהליך יצירת עסקה ב־Supabase

יש לעדכן את תהליך שמירת העסקה כך שיעבוד מול Supabase בלבד.

אין לבצע בשלב זה שום פעולה מול Monday.

## מטרת השלב

בעת פתיחת עסקה מתוך גרסת הצעת מחיר מאושרת:

1. לוודא שגרסת ההצעה תקינה.
2. לאתר או ליצור לקוח.
3. ליצור עסקה אחת בלבד.
4. לשמור את הקישור לגרסת ההצעה המאושרת.
5. לאפשר לטריגר הקיים ב־Supabase להעתיק את ה־Snapshots לעסקה.

בשלב זה אין ליצור:

* תשלום.
* קרדיטים.
* משימות תיאום.
* פריטים חדשים בטבלאות Monday.
* קריאות Webhook או API ל־Monday.

---

## 1. בדיקת גרסת הצעת המחיר

הפעולה מקבלת:

```ts
quoteVersionId: string
```

יש לטעון רשומה מתוך:

```text
quote_versions
```

לפי:

```text
id = quoteVersionId
```

ולוודא:

```text
status = 'approved'
approved_at IS NOT NULL
locked_at IS NOT NULL
```

אם אחד התנאים לא מתקיים, יש לעצור ולהחזיר שגיאה:

```json
{
  "success": false,
  "code": "QUOTE_VERSION_NOT_APPROVED",
  "message": "ניתן לפתוח עסקה רק מגרסת הצעת מחיר מאושרת ונעולה."
}
```

אין לאשר הצעה אוטומטית ואין לשנות את סטטוס גרסת ההצעה.

---

## 2. מניעת יצירת עסקה כפולה

לפני יצירת עסקה חדשה, יש לבדוק האם כבר קיימת עסקה פעילה שבה:

```text
deals.source_quote_version_id = quoteVersionId
deals.deleted_at IS NULL
```

אם קיימת עסקה, אין ליצור עסקה נוספת.

יש להחזיר את העסקה הקיימת:

```json
{
  "success": true,
  "alreadyExists": true,
  "dealId": "existing-deal-id"
}
```

בנוסף קיימת הגנת Unique בבסיס הנתונים. יש לטפל גם בשגיאת Unique Constraint כתוצאה מקריאות מקבילות ולהחזיר את העסקה הקיימת.

---

## 3. זיהוי הצד בהצעה

יש לקרוא את:

```text
quote_versions.party_snapshot
```

ה־Snapshot יכול לייצג:

* לקוח קיים.
* ליד קיים.
* פרטים שהוזנו בהצעת המחיר.

יש להשתמש במזהים הקיימים ב־Snapshot כאשר הם זמינים:

```text
customer_id
lead_id
```

אין לזהות לקוח לפי שם בלבד.

---

## 4. איתור או יצירת לקוח

### מקרה א׳ – קיים customer_id

אם קיים `customer_id` ב־`party_snapshot`:

1. יש לטעון את הלקוח.
2. לוודא שהוא פעיל:

```text
deleted_at IS NULL
```

3. להשתמש בלקוח הקיים.

אין ליצור לקוח חדש.

### מקרה ב׳ – קיים lead_id

אם אין `customer_id`, אך קיים `lead_id`:

1. יש לטעון את הליד.
2. לבדוק האם קיים:

```text
leads.linked_customer_id
```

3. אם קיים לקוח פעיל במזהה זה, להשתמש בו.
4. אם אין, לבדוק אם קיים לקוח פעיל שבו:

```text
customers.lead_id = lead_id
```

5. אם נמצא, להשתמש בו ולעדכן במידת הצורך:

```text
leads.linked_customer_id = customer.id
```

6. אם לא נמצא לקוח, ליצור לקוח חדש.

בעת יצירת לקוח מליד:

```text
customers.name = party_snapshot.name או leads.name
customers.phone = party_snapshot.phone או leads.phone
customers.email = party_snapshot.email או leads.email
customers.lead_id = lead_id
customers.joined_at = current timestamp
```

לאחר יצירת הלקוח:

```text
leads.linked_customer_id = newCustomer.id
```

יש לבצע את היצירה באופן שמטפל ב־Unique Constraint על:

```text
customers.lead_id
```

אם נוצר לקוח במקביל על ידי בקשה אחרת, יש לטעון את הלקוח שכבר נוצר ולהשתמש בו.

### מקרה ג׳ – אין customer_id ואין lead_id

אם אין מזהה לקוח ואין מזהה ליד:

1. לנרמל את מספר הטלפון.
2. לבדוק לקוח פעיל לפי:

```text
customers.normalized_phone
```

3. אם נמצא לקוח אחד ברור, להשתמש בו.
4. אם לא נמצא, ליצור לקוח חדש.

אין לאחד אוטומטית כמה לקוחות אם נמצאו כמה התאמות.

---

## 5. נרמול טלפון

יש ליישם פונקציה אחת משותפת לנרמול טלפונים ישראליים.

דוגמאות:

```text
050-123-4567 → 0501234567
050 123 4567 → 0501234567
+972501234567 → 0501234567
972501234567 → 0501234567
```

יש להסיר:

* רווחים.
* מקפים.
* סוגריים.
* תווים שאינם ספרות.
* קידומת ישראל `972`, ולהמיר אותה ל־`0`.

בעת יצירת או עדכון לקוח יש לשמור:

```text
customers.normalized_phone
```

אין לשנות את `customers.phone` לפורמט אחר ללא צורך.

---

## 6. יצירת העסקה

יש ליצור רשומה ב־`deals` עם השדות הבאים:

```text
quote_id = quote_versions.quote_id
source_quote_version_id = quote_versions.id
customer_id = resolvedCustomer.id
lead_id = resolvedLeadId, אם קיים
salesperson_id = איש המכירות שנבחר בטופס, אם קיים
salesperson_user_id = המשתמש המחובר, בהתאם למבנה הקיים
purchase_date = תאריך העסקה מהטופס או current_date
```

יש לשמור את שדות הסכומים מתוך טופס העסקה בהתאם למבנה הקיים:

```text
total_amount
total_amount_including_vat
amount_paid_including_vat
payment_type
installments_count
invoice_name
invoice_id_number
invoice_email
coordination_tasks_requested
```

אין לשלוח ידנית את שדות ה־Snapshot הבאים:

```text
party_snapshot
items_snapshot
totals_snapshot
terms_snapshot
notes_snapshot
snapshot_locked_at
```

הטריגר הקיים ב־Supabase אמור למלא אותם מתוך `quote_versions`.

אם הטריגר לא מילא את ה־Snapshots, יש לבטל את הפעולה ולהחזיר שגיאה. אין להעתיק אותם בצד הלקוח כפתרון חלופי.

---

## 7. אימות לאחר יצירת העסקה

לאחר פעולת ה־Insert יש לטעון מחדש את העסקה ולוודא:

```text
source_quote_version_id IS NOT NULL
snapshot_locked_at IS NOT NULL
items_snapshot IS NOT NULL
party_snapshot IS NOT NULL
totals_snapshot IS NOT NULL
```

אם אחד מהם חסר:

```json
{
  "success": false,
  "code": "DEAL_SNAPSHOT_CREATION_FAILED",
  "message": "העסקה לא נוצרה עם Snapshot תקין של הצעת המחיר."
}
```

במקרה כזה אין להשאיר עסקה חלקית.

---

## 8. אטומיות

תהליך יצירת הלקוח, קישור הליד ויצירת העסקה צריך להתבצע באופן אטומי.

העדיפות היא ליצור פונקציית Supabase RPC ייעודית, כך שכל הפעולות ירוצו בתוך Transaction אחד.

אין לבצע סדרת קריאות עצמאיות מהדפדפן שעלולה להשאיר:

* לקוח ללא עסקה.
* ליד עם קישור חלקי.
* עסקה ללא Snapshot.

ה־UI צריך לקרוא לפעולת Server אחת בלבד.

## 11. בדיקות חובה

### בדיקה 1

גרסה מאושרת ונעולה עם לקוח קיים:

* לא נוצר לקוח חדש.
* נוצרת עסקה.
* ה־Snapshot מתמלא.

### בדיקה 2

גרסה מאושרת עם ליד שאין לו לקוח:

* נוצר לקוח אחד.
* הלקוח מקושר לליד.
* הליד מקושר ללקוח.
* נוצרת עסקה.

### בדיקה 3

לחיצה כפולה על שמירת העסקה:

* נוצרת עסקה אחת בלבד.
* הקריאה השנייה מחזירה את העסקה הקיימת.

### בדיקה 4

שתי בקשות מקבילות מאותו ליד:

* נוצר לקוח אחד בלבד.
* נוצרת עסקה אחת בלבד.

### בדיקה 5

גרסת הצעה במצב `sent`:

* העסקה אינה נוצרת.

### בדיקה 6

גרסת הצעה מאושרת אך ללא `locked_at`:

* העסקה אינה נוצרת.

### בדיקה 7

הטריגר אינו ממלא Snapshot:

* התהליך נכשל.
* לא נשארת עסקה חלקית.

בסיום העבודה יש לדווח:

1. אילו קבצים שונו.
2. האם נוצרה פונקציית RPC.
3. כיצד מתבצעת מניעת כפילות.
4. כיצד מתבצע נרמול הטלפון.
5. אילו בדיקות הורצו.
6. לא לבצע מעבר לשלב התשלומים והקרדיטים.

# Build Monday Export Management and Run Tracking in Replit

Implement the application-side management interface for the Supabase-to-Monday deal export process.

The application already uses Supabase as its database.

The following tables already exist:

* `monday_export_targets`
* `monday_export_field_mappings`
* `monday_export_runs`
* `monday_export_run_steps`
* `monday_export_run_items`
* `monday_entity_links`
* `monday_export_run_logs`

The following view also exists:

* `monday_export_runs_overview`

Do not recreate or rename these tables.

## Important Architecture Rules

Replit is responsible for:

* Managing Monday export configuration.
* Displaying export runs and their progress.
* Creating new export run records.
* Triggering the CodeWords webhook.
* Providing retry, resume and dry-run actions.
* Displaying logs, steps and item-level results.

CodeWords is responsible for:

* Reading the deal data from Supabase.
* Transforming the data.
* Creating or updating Monday items.
* Updating run, step, item and log records.
* Retry and recovery execution logic.

Do not implement the actual Monday synchronization logic inside Replit.

Do not call Monday APIs directly from the Replit frontend.

Do not use database triggers to launch the export.

## General UI Requirements

The entire interface must be in Hebrew.

Use full RTL layout.

All labels, buttons, validation messages, tables, dialogs and notifications must be in Hebrew.

Use the existing application design system and components.

Keep the implementation simple, stable and easy to maintain.

Do not introduce unnecessary dependencies.

Use Supabase through the application’s existing server-side data layer.

Never expose the Supabase service role key or the CodeWords webhook secret to the browser.

## Navigation

Add a new administration section:

`ניהול > אינטגרציות > Monday`

Inside it, create the following tabs:

1. יעדי סנכרון
2. מיפוי שדות
3. ריצות
4. בדיקת הגדרות

Also add a Monday export section inside the deal details screen.

## Status Labels

Use Hebrew labels:

* `pending` → ממתין
* `queued` → בתור
* `running` → פועל
* `waiting` → ממתין להמשך
* `completed` → הושלם
* `completed_with_warnings` → הושלם עם אזהרות
* `failed` → נכשל
* `cancelled` → בוטל

Use consistent status badges.

## Run Actions

Display actions according to status.

### View Details

Available for every run.

### Retry

Available for:

* failed
* completed_with_warnings
* completed

This must create a new run record.

Do not reset or modify the old run.

The new record must contain:

* Same `deal_id`
* `action_type = retry`
* `status = pending`
* `parent_run_id = previous run id`
* New `run_number`
* Relevant execution options in `execution_context`

Then call the CodeWords webhook with the new run ID.

### Resume

Available for:

* failed
* waiting

Create a new run:

* `action_type = resume`
* `status = pending`
* `parent_run_id = previous run id`
* `execution_context.retry_failed_only = true`

Then call CodeWords.

### Dry Run

Allow launching a new dry run.

Create a new run with:

```json
{
  "dry_run": true,
  "force_update": false,
  "retry_failed_only": false
}
```

### Cancel

Only allow cancellation when the run is:

* pending
* queued

Update status to `cancelled`.

Do not allow frontend cancellation of a currently running CodeWords execution unless a cancellation API is explicitly added later.

# 7. Run Creation Logic

Create one server-side function or API route responsible for creating runs.

Do not create run records directly from multiple UI components.

Suggested function:

`createMondayExportRun`

Input:

```ts
type CreateMondayExportRunInput = {
  dealId: string;
  actionType: "start" | "retry" | "resume";
  parentRunId?: string;
  dryRun?: boolean;
  forceUpdate?: boolean;
  retryFailedOnly?: boolean;
  targetIds?: string[];
  continueFromStep?: string;
};
```

The function must:

1. Validate the deal exists.
2. Validate active targets exist.
3. Prevent duplicate active runs.
4. Get the next run number.
5. Insert into `monday_export_runs`.
6. Call the CodeWords webhook.
7. Return the created run.
8. If the webhook call fails:

   * Update the run to `failed`.
   * Save `error_code`.
   * Save `error_message`.
   * Save `error_details`.
   * Insert a record into `monday_export_run_logs`.

Use the existing Supabase deal table.

Do not assume its structure without checking the current database schema.

## Run Number

Use:

```sql
select public.get_next_monday_export_run_number(:deal_id);
```

Because two users may click at the same time, also handle race conditions.

If needed, retry run creation once after a duplicate run-number error.

# 8. CodeWords Webhook Integration

Create a server-side CodeWords client.

Environment variables:

* `CODEWORDS_MONDAY_EXPORT_WEBHOOK_URL`
* `CODEWORDS_MONDAY_EXPORT_WEBHOOK_SECRET`

Do not expose them to the frontend.

Send:

```json
{
  "run_id": "UUID",
  "deal_id": "UUID",
  "action": "start",
  "requested_by": "UUID",
  "options": {
    "parent_run_id": null,
    "target_ids": [],
    "continue_from_step": null,
    "retry_failed_only": false,
    "force_update": false,
    "dry_run": false
  }
}
```

Send authentication through a server-side header.

Suggested headers:

```text
Content-Type: application/json
X-Webhook-Secret: <secret>
X-Request-Id: <run_id>
```

Use a reasonable request timeout.

The webhook should only confirm that the execution was accepted.

Do not keep the browser request open until CodeWords completes the process.

After the webhook accepts the run:

* Set the run status to `queued` if CodeWords does not update it immediately.
* Store the external execution ID if returned.

# 9. Live Progress

The runs screen and run details screen should update automatically.

Prefer Supabase Realtime if it is already configured in the project.

Subscribe to changes in:

* `monday_export_runs`
* `monday_export_run_steps`
* `monday_export_run_items`
* `monday_export_run_logs`

If Realtime is not available, use polling every 5 seconds only while a run is active.

Stop polling when the run reaches a final state.

Final states:

* completed
* completed_with_warnings
* failed
* cancelled

Do not refresh the full page.

# 12. Acceptance Criteria

The feature is complete only when:

1. An admin can manage Monday export targets.
2. An admin can manage field mappings.
3. An admin can validate the configuration.
4. A user can start an export from a deal.
5. Replit creates a valid `monday_export_runs` record.
6. Replit calls CodeWords securely from the server.
7. The user can see live run progress.
8. The user can open full run details.
9. Steps, items and logs are displayed.
10. Retry creates a new linked run.
11. Resume creates a new linked run.
12. Dry run is supported.
13. Duplicate active runs are prevented.
14. No Monday API token or CodeWords secret is exposed to the browser.
15. The entire interface is Hebrew and full RTL.
16. Existing application functionality remains unchanged.

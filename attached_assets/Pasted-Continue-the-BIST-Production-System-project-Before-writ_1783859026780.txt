- Two triggers already exist on deals and do the heavy lifting — build your code around them, do not duplicate their logic in application code:
  - trg_populate_deal_snapshots_from_quote_version (BEFORE INSERT): if you insert a deals row with source_quote_version_id set, it automatically validates that quote_versions.status = 'approved' and locked_at is not null (raising a Postgres exception otherwise), then copies quote_id, party_snapshot, items_snapshot, totals_snapshot, terms_snapshot, notes_snapshot from that quote_versions row, and sets snapshot_locked_at.   - trg_protect_deal_snapshots (BEFORE UPDATE): once a deal has a non-null source_quote_version_id, it blocks any UPDATE that changes quote_id, source_quote_version_id, or any of the 5 snapshot columns, raising a Postgres exception. Your edit UI must never attempt to change those fields on a quote-based deal.
- There is a unique index on source_quote_version_id (partial, excludes NULLs) — inserting a second deal with the same source_quote_version_id raises a Postgres unique-violation.
- deals does NOT have a source_quote_id column (reuse quote_id) and does NOT have an operation_notes column (reuse special_notes for internal/operations notes).

Error handling — catch these specific Postgres errors from the trigger/constraint and map them to Hebrew messages, instead of showing a raw DB error:
- unique_violation on the source_quote_version_id index → "כבר קיימת עסקה עבור גרסת הצעה זו"

- exception text "Deal snapshots and source quote reference cannot be modified after creation" → should never be reachable from the UI, but if it is, show a generic Hebrew error and log it

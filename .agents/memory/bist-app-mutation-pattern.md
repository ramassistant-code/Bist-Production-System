---
name: bist-app mutation pattern
description: When to use apiFetch (Express API) vs Supabase client directly for mutations and combos in bist-app
---

## Rule
- **app_users** (salespersons/managers): RLS blocks Supabase anon client — always fetch via `apiFetch("/api/users")` (Express).
- **lookup_* tables**: RLS blocks Supabase anon client — fetch via `apiFetch("/api/lookups/:table")` (Express). ALLOWED_TABLES list in `artifacts/api-server/src/routes/lookups.ts`.
- **customers** combo: can use Supabase directly (authenticated JWT session allows read).
- **leads** combo: can use Supabase directly.
- **customer mutations**: use `apiFetch("/api/customers", POST)` / `apiFetch("/api/customers/:id", PATCH)` — Express generates `customer_number` (NOT NULL, no DB trigger).
- **lead mutations**: use Supabase directly (`supabase.from("leads").update/insert`) — `lead_number` is generated by DB trigger (not Express).

## Shared utility
`artifacts/bist-app/src/lib/api-fetch.ts` — `apiFetch<T>(path, { method?, body? })` sends Bearer token + Content-Type JSON. Use for all Express API calls.

**Why:**
RLS on app_users and lookup tables has no anon-read policy. customer_number has no DB trigger (generated in Express). lead_number DOES have a DB trigger so Supabase insert works.

**How to apply:**
Any new combo that reads app_users → Express API. Any new lookup dropdown → `/api/lookups/:table` (add table name to ALLOWED_TABLES). Mutations on customers → Express. Mutations on leads → Supabase.
